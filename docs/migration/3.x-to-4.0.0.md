# Migrating from onFHIR 3.x to the reusable libraries 4.0.0

This guide is for applications that depend on `io.onfhir` artifacts from the
3.x onFHIR monorepo line and are upgrading to the independently released
reusable libraries, version `4.0.0`, published from the `srdc/onfhir-libs`
repository.

## 1. Overview

In 4.0.0 the onFHIR monorepo was split into two independently versioned
products:

- **The reusable libraries** (this repository): FHIR models and utilities,
  FHIRPath, query parsing and in-memory matching, configuration,
  expression dispatch, validation, template engine, R4/R5/STU3 foundation
  parsers, packaged FHIR definitions, and the HTTP client. Licensed
  **Apache-2.0**, transport-neutral, and free of Akka and Pekko.
- **The Repofyr server** (the onFHIR FHIR server's continuation, in its own
  repository): HTTP routing, persistence, subscriptions, auditing,
  authorization runtime, Kafka integration, and server lifecycle. Licensed
  **GPL-3.0**, published under `io.repofyr` Maven coordinates.

If your application only consumes library APIs, this guide is everything you
need. If it also touches server runtime types (see section 5.2), those types
now live in Repofyr under the GPL-3.0 license, which is a dependency decision
to make deliberately, not a mechanical migration step.

## 2. Version and compatibility policy

- `4.0.0` is an intentional **major** release. Except for
  `onfhir-expression`, which is binary compatible with 3.3, every artifact
  contains breaking changes; plan to recompile, not to drop JARs in place.
- Going forward, all coordinates release together at one version, and
  binary breaks occur only in a major release: `4.x.0` minors are additive
  and backward binary-compatible, `4.0.x` patches are fixes only. A
  binary-compatibility gate enforces this on every build, so within the
  `4.x` line you can bump versions without recompiling against a changed
  API. Deprecations are announced in a minor and removed no earlier than
  the next major.
- Every binary break relative to the last public monorepo release (`3.3`) is
  machine-recorded in
  [`docs/compatibility/mima-3.3-accepted.txt`](../compatibility/mima-3.3-accepted.txt)
  and grouped, with pointers back into this guide, in the
  [MiMa reconciliation](../compatibility/mima-3.3-reconciliation.md).
- Maven group (`io.onfhir`), artifact IDs, and `io.onfhir.*` package roots
  are preserved for the library family, with the single artifact-ID
  correction described in section 3.1.
- Scala binary version remains `2.13`; bytecode targets Java 11.

### 3.2 The BOM

Applications using several modules can import the BOM once and omit
per-dependency versions:

```xml
<dependencyManagement>
  <dependencies>
    <dependency>
      <groupId>io.onfhir</groupId>
      <artifactId>onfhir-libs-bom</artifactId>
      <version>4.0.0</version>
      <type>pom</type>
      <scope>import</scope>
    </dependency>
  </dependencies>
</dependencyManagement>
```

provided by the library artifacts above.

## 4. Dependency and packaging changes

### 4.1 Akka and Pekko removed

Library production sources, resources, and the complete resolved dependency
graph contain no Akka or Pekko. Consequences for consumers:

- No Akka types appear in any library signature (section 6.1 lists the
  replacements).
- The client no longer needs an `ActorSystem` (section 6.2).
- If your application relied on Akka artifacts arriving transitively through
  onFHIR dependencies, declare them yourself.

### 4.2 Logging: bring your own SLF4J provider

3.x libraries exported Logback as a transitive SLF4J provider. 4.0.0 modules
declare only `slf4j-api`; the consuming application selects one provider at
deployment time.

```xml
<!-- 3.x: Logback arrived transitively. 4.0.0: declare a provider yourself. -->
<dependency>
  <groupId>ch.qos.logback</groupId>
  <artifactId>logback-classic</artifactId>
  <version>1.5.18</version>
</dependency>
```

Applications that do not install a provider get SLF4J's no-operation
fallback (a one-line warning and silence), not a failure.

### 4.3 onfhir-path no longer packages grammar files

3.x published the ANTLR grammar (`/FhirPathExpr.g4`), the generated
`.tokens` files, and the 1.95 MB `antlr-4.7-complete.jar` build tool as
classpath resources inside `onfhir-path`. 4.0.0 packages none of them; the
artifact carries only compiled classes. Nothing in the library loaded these
files at runtime. A consumer that read them off the `onfhir-path` classpath
must vendor its own copies.

### 4.4 FHIR definitions artifacts

The FHIR standard definitions that server modules previously embedded are now
standalone resources-only artifacts (section 3.1). Packaged file names carry
the FHIR release so the artifacts can share a classpath:

| Classpath resource | Artifact |
|---|---|
| `definitions-r4.json.zip`, `conformance-statement-r4.json` | `onfhir-definitions-r4` |
| `definitions-r5.json.zip`, `conformance-statement-r5.json` | `onfhir-definitions-r5` |
| `definitions-stu3.json.zip`, `conformance-statement-stu3.json` | `onfhir-definitions-stu3` |

Code that loaded the server's old release-agnostic names
(`definitions.json.zip`, `conformance-statement.json`) must switch to the
release-qualified names. The library configuration readers
(`FSConfigReader`/`BaseConfigReader`) already default to the qualified names.
The packaged HL7 content is CC0 1.0, recorded in `NOTICE`.

## 5. Relocated classes

### 5.1 Within the library family

Packages are unchanged; only the owning artifact moved. Consumers relying on
transitive availability through `onfhir-common` must add a direct dependency
on the new owner:

| Classes | Old artifact | New artifact |
|---|---|---|
| `io.onfhir.api.client.*` (request builders, client API model) | `onfhir-common_2.13` | `onfhir-client_2.13` |
| `FhirQueryParser`, `FHIRResultParameterResolver` | `onfhir-common_2.13` | `onfhir-query_2.13` |
| `ImMemorySearchUtil`, `InMemoryPrefixModifierHandler` | `onfhir-common_2.13` | `onfhir-query_2.13` |
| `io.onfhir.validation.BaseFhirProfileHandler` | `onfhir-validation_2.13` | `onfhir-config_2.13` |

`BaseFhirProfileHandler` keeps its `io.onfhir.validation` package; declare a
direct `onfhir-config_2.13` dependency and see section 6.5 for its widened
constructor.

### 5.2 Moved to the Repofyr server (GPL-3.0)

The following left the library family entirely. They are server runtime
concerns and now live in Repofyr (section 3.3), under `io.repofyr.*`
packages:

| Classes | Old artifact | Repofyr artifact |
|---|---|---|
| `io.onfhir.event.*`, `InternalJsonMarshallers` | `onfhir-common_2.13` | `repofyr-event_2.13` |
| `io.onfhir.audit.*`, `io.onfhir.db.*` | `onfhir-common_2.13` | `repofyr-core_2.13` |
| server authorization runtime types | `onfhir-common_2.13` | `repofyr-core_2.13` |
| `AuthzConfig`, `AuditConfig`, `IFhirServerConfigurator`, `IndexConfigurator` | `onfhir-common_2.13` | `repofyr-core_2.13` |
| `IResourceSpecificValidator`, `OnfhirConfig` | `onfhir-common_2.13` | `repofyr-core_2.13` |
| the ten HTTP response exceptions (`BadRequestException`, `NotFoundException`, ...) | `onfhir-common_2.13` | `repofyr-core_2.13` |
| `SubscriptionUtil` (release-specific instances come from the server configurator) | `onfhir-common_2.13` | `repofyr-core_2.13` |
| `BaseFhirServerConfigurator` | `onfhir-config_2.13` | `repofyr-core_2.13` |
| `FHIRSearchParameterValueParserDirectives` (Akka directives wrapper) | new in 4.x | `repofyr-core_2.13` |

A library-only consumer that referenced these types was depending on server
internals; the usual fix is to migrate to the neutral equivalents (library
exceptions, section 6.2 error model; injected configuration, section 6.3)
rather than to add a GPL dependency.

## 6. Public API changes

### 6.1 Transport-neutral HTTP model

Akka HTTP types were replaced throughout public signatures, primarily in
`FHIRRequest`/`FHIRResponse` and their helpers in `onfhir-common`:

| 3.x (Akka) | 4.0.0 replacement |
|---|---|
| `akka.http.scaladsl.model.Uri` | `java.net.URI` |
| `Uri.Query` | `OrderedQuery` (preserves order, duplicates, encoding, missing-vs-empty) |
| `DateTime` | `java.time.Instant` |
| `StatusCode` | `HttpStatus` (any 100-599, family classification) |
| `HttpMethod` | neutral `HttpMethod` (validated token, extension methods allowed) |
| `MediaType` / `ContentType` constants and config | `FhirMediaType` / `FhirContentType` |
| ETag headers | `EntityTag` / `EntityTagCondition` (explicit weak/strong, wildcard variants) |
| `WWW-Authenticate` challenges | `AuthenticateChallenge` |
| forwarded-for/host header types | `ForwardedFor` / `ForwardedHost` |
| `DateTimeUtil.parseHttpDateToDateTime(String): DateTime` | `DateTimeUtil.parseHttpDate(String): Instant` |
| `IFhirAuditCreator` methods taking `StatusCode` | `HttpStatus` |

The semantic contract these replacements must honor (URI encoding
round-trips, duplicate query keys, weak entity tags, HTTP-date second
precision and its non-applicability to FHIR `instant`/`dateTime` values) is
specified in [ADR 0001](../adr/0001-neutral-http-contract.md).

### 6.2 onfhir-client

The client was rewritten on `java.net.http` (JDK 11+ HttpClient). The fluent
request-builder API is unchanged in shape; construction and the extension
points changed:

```scala
// 3.x
implicit val actorSystem: ActorSystem = ActorSystem("fhir-client")
val client = OnFhirNetworkClient("https://fhir.example.com/fhir")

// 4.0.0
implicit val executionContext: ExecutionContext = ExecutionContext.global
val client = OnFhirNetworkClient("https://fhir.example.com/fhir")
```

- `OnFhirNetworkClient` and `FhirClientUtil` factories take an implicit
  `ExecutionContext` instead of an implicit `ActorSystem`.
- `OnFhirNetworkClient` is a normal final class now, not a case class; the
  `copy`/`unapply` surface is gone. Use the factories
  (`OnFhirNetworkClient(baseUrl)`, `...(baseUrl, interceptor)`,
  `...(baseUrl, settings)`, `...(config)`).
- Interceptors receive the neutral `ClientHttpRequest` instead of an Akka
  `HttpRequest`. `BearerTokenInterceptorFromTokenEndpoint.getToken` became
  asynchronous: `getToken(): Future[String]` with single-flight refresh.
- HTTP transport configuration moved from `akka.http.client` /
  `akka.http.host-connection-pool` to `onfhir.client.http` (connect timeout,
  optional request timeout, retry settings) or programmatic
  `ClientHttpSettings`.
- `FhirReadRequestBuilder.ifModifiedSince` takes `Instant`;
  `FHIRHistoryBundle` history timestamps are `Instant`.
- Error model: client misuse and error responses surface as
  `FhirClientException`; the client no longer throws the server's HTTP
  exceptions (which moved to Repofyr, section 5.2). Bundle parsing problems
  raise `BundleRequestParsingException`.
- `executeAndReturnOperationOutcome` now fails the returned `Future` for an
  error response status instead of materializing it as a successful result;
  handle it with `recover`, where the failure carries the outcome.

See the [onfhir-client README](../../onfhir-client/README.md) for the full
current API, authentication interceptors, and configuration reference.

### 6.3 Configuration-injected constructors

3.x library classes read request-handling defaults from the server's global
`OnfhirConfig` singleton. 4.0.0 removes that hidden coupling: the values are
small, explicit constructor parameters. The parameter types live in
`onfhir-common` (`FhirSearchHandling`, `FhirEndpointSettings`,
`FhirResultDefaults`, `FhirSubscriptionSettings`, `FhirCapabilityDefaults`,
`FhirReturnPreference`):

| 3.x | 4.0.0 |
|---|---|
| `new FHIRSearchParameterValueParser(config)` | `new FHIRSearchParameterValueParser(config, searchHandling)` |
| `new FhirQueryParser(config)` | `new FhirQueryParser(config, searchHandling)` |
| `new XFhirQueryParser(config, fhirPathEvaluator)` | `new XFhirQueryParser(config, searchHandling, fhirPathEvaluator)` |
| `new FHIRResultParameterResolver(config)` | `new FHIRResultParameterResolver(config, resultDefaults)` |
| `BundleRequestParser.parseBundleRequest(bundle, prefer, skip)` | `parseBundleRequest(bundle, endpointSettings, prefer, skip)` (same pattern for `parseBundleRequestEntry`, `parseUrl`) |
| `FHIRRequest.initializeTransactionOrBatchRequest(resource, prefer)` | `initializeTransactionOrBatchRequest(resource, endpointSettings, prefer)` |
| `FHIRUtil.resourceLocation(type, id)` | `resourceLocation(endpointSettings, type, id)` (same for `resourceLocationWithVersion`) |
| `FHIRUtil.getResourceContentByPreference(resource, prefer)` | `getResourceContentByPreference(resource, prefer, returnPreference)` |
| `ImMemorySearchUtil.handleSimpleParameter(...)` / `handleCompositeParameter(...)` | add `FhirEndpointSettings` (and moved to `onfhir-query`) |
| `IFhirVersionConfigurator.getFoundationResourceParser(complex, primitive)` | `getFoundationResourceParser(complex, primitive, capabilityDefaults)` |
| `new R4Parser(complex, primitive)` | optional third `FhirCapabilityDefaults` argument; the historical `Standard` default applies when omitted |
| `new BaseFhirProfileHandler(FhirServerConfig)` | `new BaseFhirProfileHandler(BaseFhirConfig)` - widened; existing callers pass their subtype unchanged |

Structure-definition parsers also carry element metadata through
`parseElement`-family signatures, and `FhirContentValidator` accepts an
optional local endpoint in its validation context.

### 6.4 FHIRPath (onfhir-path)

Additive, per the FHIRPath Normative 1 specification:
`convertsToBoolean`, `convertsToInteger`, `convertsToDate`,
`convertsToDateTime`, `convertsToQuantity` (same-unit only, no general UCUM
conversion), `convertsToString`, `convertsToTime`, `toTime`, `toChars`,
`union(other)`, and `timeOfDay()`.

Behavior changes:

- `toInteger`/`toDecimal` on an invalid numeric string return empty instead
  of throwing.
- `Boolean.toString` inside expressions yields `true`/`false` without
  embedded apostrophe delimiters.
- `now()`, `today()`, and `timeOfDay()` share one clock sample within a
  single expression evaluation instead of being sampled independently.
- Time-offset literals are accepted.
- **Security fix:** a `%name` environment variable that no caller supplied
  no longer falls through to the OS process environment (`sys.env`).
  FHIRPath expressions arrive from profile invariants, search parameter
  definitions, subscription criteria, and mapping templates, so the
  fallthrough allowed content the operator did not author to read process
  secrets and surface them through validation diagnostics or mapped
  resources. A deployment that relied on it must supply the value explicitly
  with `withEnvironmentVariable`. An unsupplied variable now resolves to
  empty (see [known limitations](../release/known-limitations.md), entry 5,
  for why it is empty rather than the spec-required error).

### 6.5 Validation (onfhir-validation)

- New recommended entry point: the `FhirValidator` facade
  (`FhirValidator(BaseFhirConfig, external terminology services, optional
  IExternalFhirReferenceResolver)`) with resource-type/profile selection,
  terminology composition, recursive resource validation, and library-owned
  contained/Bundle reference resolution. Low-level `FhirContentValidator`
  construction remains available.
- `BaseFhirProfileHandler` moved to `onfhir-config` (section 5.1) and takes
  `BaseFhirConfig` (section 6.3).
- Validator runs reset their per-run state, so an instance can be reused
  across resources.

### 6.6 Query (onfhir-query)

New artifact collecting what 3.x spread across `onfhir-common`: query and
x-fhir-query parsing, result-parameter resolution, and in-memory matching.
The `FhirQueryEvaluator` facade in `io.onfhir.query` parses once and compiles
a query into a reusable, thread-safe `CompiledFhirQuery` predicate
(subscription criteria, conditional operations, and CDS filtering evaluate
one query against many resources). See the
[onfhir-query README](../../onfhir-query/README.md) for supported parameter
types and in-memory matching semantics.

### 6.7 Expression (onfhir-expression)

Binary compatible with 3.3. One behavioral change:
`FhirExpressionEvaluator.evaluateExpression`/`satisfies` report an
unregistered expression language through the returned failed `Future`
instead of throwing synchronously. A caller that wrapped the call site in
`try`/`catch` must handle the failed `Future` (`recover`) instead.
`validateExpression` still throws, because it returns `Unit`.

### 6.8 Data model changes

- `FHIRSearchParameter.components` changed from `Set[String]` to
  `Seq[String]`. A composite search statement binds its `$`-separated value
  parts to the components positionally, which an unordered set cannot
  express. Pass components in declaration order; `copy`/`apply` signatures
  changed accordingly.
- Authorization and operation models continue their 3.3-to-4.0 evolution on
  the release line: `AuthzContext` carries JSON-valued parameters and
  `AuthzConstraints`; `OperationConf`/`OperationParamDef` are level-aware;
  `ElementRestrictions` carries string profile provenance. Consumers of
  these models must recompile against the new signatures.

## 7. Upgrade recipe

1. Bump `io.onfhir` dependencies to `4.0.0` (or import the BOM, section
   3.2). Rename `onfhir-template-engine` to `onfhir-template-engine_2.13`.
2. Add an SLF4J provider (section 4.2) and any Akka artifacts you were
   getting transitively (section 4.1).
3. Add direct dependencies for relocated classes you use (section 5.1).
4. If you referenced server runtime types, decide between migrating to the
   neutral equivalents or depending on GPL-3.0 Repofyr artifacts
   (section 5.2).
5. Recompile. Fix the mechanical signature changes as the compiler reports
   them, using section 6 as the reference: Akka HTTP types (6.1), client
   construction and interceptors (6.2), configuration-injected constructors
   (6.3), `components` ordering (6.8).
6. Review the behavioral changes that compile cleanly but act differently:
   FHIRPath conversions and environment variables (6.4), expression facade
   error reporting (6.7), client `executeAndReturnOperationOutcome` (6.2).
7. Run your test suite. For validation-heavy applications, also review
   [known limitations](../release/known-limitations.md).
